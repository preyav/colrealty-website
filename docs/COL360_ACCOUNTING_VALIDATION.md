# COL360: entity-scoped cash and accrual accounting

## What changed

Financials defaults to the entity's configurable reporting basis, initially cash. A global initial fallback is stored in Form field settings → accounting_books → defaults. Each entity has its own default basis. Financials and General Ledger offer both bases and require one entity once entities have been configured.

The original rent, vendor invoice, vendor payment, allocation, chart-account and journal records remain the source records. This change creates no company, bank balance, historical payment or opening journal. Schema migrations add tables; they do not convert business data.

A source can generate multiple balanced journal entries, each linked to its entity and reporting basis. A cash report never adds accrual entries to cash entries. An accrual report never adds cash entries. Financials remains a property income/expense report, not the bank balance or tenant ledger.

Operational dates remain distinct:

- Rent charges retain their service start/end and due date. Accrual recognition uses service start. Early receipts are advance liabilities in accrual books until service begins; their release is dated to service start.
- Payments retain actual receipt/payment dates. Cash income is recognized when an identified rent payment was received; unknown/unallocated amounts remain client credits until classified.
- Vendor bills retain invoice/due dates. New bill accounting metadata supplies the service start/end, explicit recognition date and expense account. These dates are not guessed from the payment date.
- Refunds, credits and client-funds applications are separate immutable records. They do not rewrite the original charge/payment date or amount.

## Local installation

Back up the local PostgreSQL database before applying schema migrations. This is an additive development change; do not run it directly on EC2.

```powershell
git apply --check --ignore-space-change COL360_Entity_Cash_Accrual_Accounting.patch
```

The patch intentionally does not guess the next migration dependency: previous migrations were generated in your local repository. Inspect and commit the migration generated by your actual project. It should create the new accounting tables and must not drop or alter existing monetary records. Commit that same migration for Render and EC2; do not generate different migrations in each environment.

## Configure before enabling posting

Django admin → Accounting:

1. **Accounting entities:** create the actual legal/accounting entities and select each reporting default. Reports do not combine entities. Archived entities remain available for historical reporting.
2. **Entity banks:** assign each existing physical Financial Account to its owning entity. One bank account cannot belong to two entities. A trust bank can serve several properties within one entity; property balances remain separate.
3. **Property books:** assign the property to its entity and select existing chart accounts for rent income, receivables, payables, refundable deposits, advance rent, unapplied client credits and owner equity. Control accounts must be distinct and of the correct type. Set the actual reserve. Leave Enabled unchecked while reviewing history.
4. **Bill accounting:** supply the actual service period, recognition date and expense account for each approved bill that will be posted.
5. **Form field settings:** labels/options remain configurable. Operating vs non-operating income/expense classification remains under financial_account_classification, using operating or non_operating; unknown classifications do not produce an invented net operating income.

Only enable a property's books after reviewing its existing journals and source history. No account codes, company names, bank details, rent amounts or reserve amounts are inferred from the Killians example.

## Existing records and first posting

Open Accounting → Accounting operations and choose an entity.

- The readiness command identifies unposted sources and unassigned journals without changing them.
- Use **Assign a reviewed existing journal** only after confirming its entity and basis. It attaches the existing journal unchanged. It does not copy the journal or invent a matching source. Reversed original/correction pairs require a combined review and cannot be assigned individually through this action.
- If an existing journal already represents a rent payment or bill, **do not also import that source**. The same financial event must not be recorded twice. Automatic matching of historical/manual journals to operational sources is deliberately not performed. Unresolved matches keep owner funds provisional and require a reviewed migration plan.
- **Post reviewed source** is explicit and idempotent. It records journal links and preserves the source. Check the original document/bank record and the existing ledger first. Missing bank ownership or bill service metadata blocks posting instead of guessing.
- Once a property is enabled, newly created rent charges/payments and later credit allocations post transactionally. Existing historical sources are not bulk-posted by enabling it.
- Vendor bills/payments currently use the explicit reviewed posting queue. Their original maintenance/payment workflows remain intact; this change does not silently introduce a second bank transaction or duplicate QuickBooks synchronization.
- A posted rent source cannot be edited in place. Void and replace an erroneous entry; linked journals reverse together. Paid charges and entries with client-funds refunds/applications are protected pending review. Correct a posted vendor payment through Accounting operations; source and books reverse together.

## Separate funds and balances

Accounting operations includes:

- Tenant unpaid charges, overdue amounts, unapplied credits, recorded refundable deposits and advance rent. Existing lease security-deposit terms are not proof a deposit was received and are not silently converted to liabilities.
- Unpaid vendor bills, due dates and remaining amounts, including separate bill credits/refunds.
- Refundable deposit receipt/refund/application, advance rent receipt/application/refund, credit refund, earned-rent refund, rent charge credit, vendor credit/refund, owner contribution/distribution.
- Client-funds applications require an original receipt and a charge for the same lease. Applications/refunds cannot exceed the original remaining funds. Earned-rent refunds identify the original paid charge and payment, preserve allocation history and reduce income without creating fictitious unpaid rent.
- Owner funds per property: actual posted cash less refundable deposit liabilities, advances, unapplied client credits, recognized unpaid bills and the configured reserve. This is not the same as net income. Missing source review or uncleared bank entries hold available distributions at zero; provisional amounts remain visible.

Owner contributions, distributions and bank transfers are balance-sheet movements, not property income or expenses. A same-entity bank transfer can be recorded as a reviewed journal in both books, debiting the receiving bank and crediting the sending bank. These actions record accounting facts; they do not send money through a bank.

## Bank reconciliation

Load the entity bank's transactions, enter the actual statement start/end and opening/closing balances, and select the entries actually cleared on that statement. Preview the difference before finalizing.

- Only cash-book bank lines for that entity/bank are eligible. Accrual mirror entries are excluded.
- A line can clear once. Outstanding items remain uncleared.
- A statement cannot overlap a finalized statement. Its opening must continue the last finalized closing.
- The first opening balance must match posted opening books; an opening value in Financial Account metadata alone is not automatically journalized.
- Finalization requires a zero difference, records the actor and locks the statement and its clearances. The system never creates a balancing plug.
- Bank-affecting postings into a finalized bank period are blocked. Corrections belong in an open period.

This is manual statement-to-ledger reconciliation. It is not a bank-feed connection, statement OCR or a bank-confirmed balance.

## Posting examples

| Event | Cash book | Accrual book |
|---|---|---|
| Rent charge/service recognition | No income yet | Debit receivable; credit rent income |
| Rent receipt, not yet identified | Debit bank; credit client credit | Debit bank; credit client credit |
| Payment identified against earned rent | Debit client credit; credit rent income, on receipt date | Debit client credit; credit receivable |
| Identified early rent payment | Recognize rent on receipt date | Move client credit to advance liability; release against receivable when service starts |
| Refundable deposit received | Debit bank; credit deposit liability | Same |
| Separately recorded advance received | Debit bank; credit rent income | Debit bank; credit advance liability |
| Advance applied to earned charge | No second income | Debit advance liability; credit receivable |
| Vendor bill recognized | No expense yet | Debit expense; credit payable |
| Vendor bill paid | Debit expense; credit bank | Debit payable; credit bank |
| Vendor credit | No cash expense adjustment until refund/payment effect | Debit payable; credit expense |
| Vendor refund | Debit bank; credit expense | Debit bank; credit payable |

## Validation gates: local → Render → EC2

### Local PostgreSQL

Run the tests above against a disposable local test database. The supplied isolated regression run uses SQLite; it does not prove PostgreSQL concurrency behavior or validate your live financial records.

On a copied/sanitized database, verify:

1. June 30 vs July 31 receipt dates, lease service periods and due dates remain distinct and unchanged on import.
2. Late rent appears in the payment month on cash reports and service month on accrual reports; early rent remains an accrual liability before service.
3. Partial payments, excess credit, separate charge credits and refunds reconcile without changing original entries.
4. A refundable deposit never becomes income until an explicit valid application; actual deposit opening balances are reviewed separately.
5. Partial vendor payments reduce payable and recognize only paid expense on cash reports. Credits/refunds do not exceed actual balances.
6. Entity/bank mismatches, stale source changes, duplicate submissions and over-refunds fail atomically.
7. Simultaneous posting/refund/reconciliation requests on PostgreSQL cannot double-allocate or clear the same line. Verify row locks and rollback/retry behavior in that environment.
8. Statement differences remain visible; nothing finalizes unless the difference is zero.
9. Source review and bank reconciliation gates prevent unsafe owner distributions.
10. Keep pre/post row counts and source totals; the existing historical records must remain present. Review every unassigned legacy journal before declaring the accounting cutover complete.

### Render staging

Deploy the committed code and the same reviewed migration to Render staging. Back up staging data, migrate, run the seed commands, inspect readiness output, and repeat the PostgreSQL and browser workflows. Check staff access, CSRF protection, duplicate submissions, source posting, both Financials bases, General Ledger drill-through, bill corrections and reconciliation. Do not enable live bank movements or send actual payments as part of this test.

### EC2 production

Only after local and Render sign-off: take a production backup, deploy the tested commit and migration, migrate, seed, check, and run the read-only readiness command. Configure/enable entities deliberately and review historical matches before the production accounting cutover. Do not automatically replay all historical payments. Record a rollback/restore plan for the migration and cutover.

## Current boundaries

This implementation does not automatically reconcile bank statements, map unidentified historical/manual journals to operational sources, post QuickBooks transactions a second time, calculate ownership-share payouts, or create payment evidence from a lease's expected rent. It does not yet provide prepaid-vendor-expense amortization, credit-card settlement accounting or arbitrary long-term accrual schedules; affected sources remain unposted with a validation error instead of being misclassified. Corrections to immutable client-funds events require an explicit matching counter-event and review; there is no destructive delete.
